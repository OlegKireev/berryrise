# Design

## Context

Мотивация в proposal.md. Что важно для подхода:

- Строки читаются через `getAllAsync<T>`/`getFirstAsync<T>` в `entities/*/api`, тип `T` из `model/types.ts` никто не проверяет. JSON-колонки типизированы как `string` с комментарием, разбирают их страницы и фичи сами (`parseList`/`parseCounts` в `useDayCard`, `useDayReview`, `useCompany`, `useInsights`, `useToday`, `useSpendingForm`).
- Писатели базы: наш код, миграции и импорт (`importBackup` вставляет строки файла как есть, ловит только NOT NULL и CHECK).
- Журнал (`shared/lib/log.ts`) не должен содержать данные пользователя (спека `error-log`).
- Асинхронные загрузки в хуках сейчас не ловят ошибки: отклоненный промис оставляет экран в состоянии "грузим".

## Goals / Non-Goals

**Goals:**

- Один источник правды для формы строки: схема, из нее тип.
- Строки наружу из `api/` выходят уже разобранными (массивы, объекты), страницы JSON не парсят.
- Мягкий фолбэк для вариантов и жесткий для скелета, с записью в журнал.
- Импорт проверяется теми же схемами.

**Non-Goals:**

- Доводить ошибку чтения до экрана ошибки (`ErrorPage`). Сейчас никакая ошибка загрузки до него не доходит, это отдельная проблема для всех хуков. Здесь достаточно не посчитать стрик без записи и записать ошибку в журнал.
- Проверять запросы, которые возвращают служебные данные (`PRAGMA`, `sqlite_master`, `SELECT 1`), и `settings`.

## Decisions

### zod, а не ручные type guard'ы и не valibot

`z.infer` дает тип из той же схемы, что проверяет, - ручные guard'ы из `shared/lib/utils/json.ts` этого не дают, тип и проверка живут отдельно. valibot меньше, но размер для RN-бандла роли не играет, а zod привычнее. Импорт `import { z } from 'zod'` (классический API: `.catch`, `.transform`, `.pick` читаются проще, чем функции `zod/mini`). zod уже лежит в lockfile транзитивно (4.x), ставим прямой зависимостью через `yarn add zod` (не expo-пакет). Нативного кода нет, dev build не пересобираем.

Риск Hermes: zod 4 ускоряет объекты генерацией кода через `new Function` и сам проверяет, доступен ли он. Первый таск - спайк в dev build: схема объекта парсится, `.catch` и `.transform` работают. Если на Hermes что-то не так, включаем `z.config({ jitless: true })` в одном месте (`shared/db`).

### Где лежат схемы

- `shared/db/schema.ts` - общие куски: `rowSchema` (`id`, `createdAt`, `updatedAt`, `deletedAt`, вместо типа `Row` в `records.ts`, сам `Row` станет `z.infer`), хелперы JSON-колонок и `parseRows`/`parseRow`. `shared/db` может зависеть от `shared/lib` (журнал).
- `entities/<x>/model/schema.ts` - схема строки сущности (`relapseSchema = rowSchema.extend({...})`), тип `Relapse = z.infer<typeof relapseSchema>`. `types.ts` остается для ключей вариантов (`drinks`, `partyDrinks`, `reasons`, `replies`).
- Варианты берутся из существующих `as const` массивов: `z.enum(places)`, для чисел настроения `z.union(moods.map(z.literal))` или `z.literal(moods)` (zod 4 принимает массив литералов).
- Схема каждой сущности экспортируется из ее `index.ts`, ей пользуется `features/backup` (фича может импортировать несколько сущностей).

### Мягко и жестко

```
поле                                      не прошло
-----------------------------------------  -----------------------------------------
элемент JSON-списка (places, drinkKeys..)  выкинуть элемент, лог info
необязательный вариант (relapse.mood)      null, лог info
битый JSON в колонке списка                пустой список, лог info
скелет и обязательные варианты             строка сломана:
  (id, *At, date, dayReview.mood/craving,    relapse, habit  -> logError + throw
   reason/reply.key при пустом customText)   остальные       -> logError, строка пропущена
```

Хелперы в `shared/db/schema.ts`:

- `jsonList(item)` - строка (или `null`) -> `JSON.parse` -> массив только из элементов, прошедших `item`. Не валит строку, а фильтрует, как сейчас `parseList`.
- `jsonCounts(keys)` - для `habit.drinks`, как `parseCounts`.
- `optional(schema)` - `schema.nullable().catch(null)`.

Сравнили с `z.array(z.enum(...))`: он валит весь массив из-за одного устаревшего ключа, а нам нужен поэлементный фильтр.

`parseRows(table, schema, rows, onBroken)` в `shared/db`: `safeParse` каждой строки, при ошибке пишет `logError('db', ...)` с таблицей, путями полей из `issues` и `id` строки (без значений) и по `onBroken` (`'throw' | 'skip'`) бросает или пропускает. `parseRow` - то же для `getFirstAsync`. В `api/` сущности каждое чтение оборачивается: `parseRows('relapse', relapseSchema, await db.getAllAsync(...), 'throw')`. Дженерик у `getAllAsync` больше не пишем, строки - `unknown`.

Все чтения сущностей - `SELECT *` и полная схема, без частичных `SELECT id, at` и `.pick`: иначе строка, которую полное чтение пропускает, попала бы в списки дат и стартов (календарь, достижения), и экраны разошлись бы. Даты вечеров в компании фильтруются по уже разобранным `places` в JS, а не через `json_each`: тот падает на битом JSON.

### Лог мягких фолбэков без данных и без спама

Фолбэк срабатывает внутри `.catch`/`.transform` поля, там не видно ни таблицы, ни `id`. Поэтому хелперы получают метку колонки (`jsonList(placeKey, 'places')`), а `parseRows` перед разбором каждой строки ставит модульную переменную "текущая таблица и id" (разбор синхронный, пересечься нечему). Лог - `log('db', ...)` уровня "событие": таблица, колонка, `id`, без значения. Дедуп - `Set` на процесс: одна запись за запуск на "таблица.колонка" для фолбэков и на "таблица:поля" для сломанных строк (экраны перечитывают базу на каждом фокусе).

Альтернатива - два прохода (строгий `safeParse`, потом мягкий) и сравнение issues: дороже и сложнее, а дает то же.

### Запись

Функции записи принимают разобранные значения (`places: Place[]`) и сами делают `JSON.stringify` (сейчас так уже у `insertRelapse`). Там, где страница сейчас передает строку JSON (`useCompany`, `startParty`), тип меняется на массив.

### Импорт

`restoreDatabase(db, version, fill, check?)` - новый необязательный колбэк после последней миграции, внутри той же транзакции. `importBackup` передает `check`, который читает все строки всех таблиц сущностей (включая удаленные) и прогоняет через `parseRows(..., 'throw')` для всех таблиц, не только `relapse`/`habit`: при импорте сломанная строка любой таблицы - это поврежденный файл. Мягкие фолбэки при этом не валят импорт, неизвестный вариант остается в базе и отбрасывается на чтении. Проверка идет после миграций, потому что схемы описывают текущую версию, а файл может быть старым.

### Тег журнала

В `LogTag` добавляется `'db'`. Экран журнала показывает теги как есть, словарь не нужен.

## Risks / Trade-offs

- [Hermes и JIT zod] -> спайк первым таском, запасной вариант `jitless`.
- [Сломанный срыв оставляет экран в "грузим" без объяснения] -> осознанно: лучше, чем неверный стрик; в журнале есть ошибка. Довести до экрана ошибки - отдельное изменение для всех загрузок.
- [Пропущенные итоги дня: пользователь видит день без итогов и заполняет заново] -> запись идет через upsert по дате и перезапишет сломанную строку, уникальный индекс не мешает.
- [Производительность: разбор каждой строки на чтении] -> строк сотни, максимум несколько тысяч за годы; проверить на статистике в спайке. Если заметно, `jitless` выключен по умолчанию и как раз ускоряет объекты.
- [Модульная переменная "текущая строка"] -> держится только пока разбор синхронный; помечаем `ponytail:` комментарием.
- [Миграция схемы БД] -> не нужна: таблицы и колонки не меняются, `PRAGMA user_version` не трогаем.
