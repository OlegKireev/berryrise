# Design

## Context

Уведомлений и `expo-notifications` в проекте нет. Настройки key/value лежат в таблице `settings` (уже используется для `customPartyDrinks`). Идущая вечеринка и ее `expectedEndAt` есть в `entities/party`, итоги дня по датам в `entities/day-review`, день для итогов считает `reviewDay(at)` (до 18:00 вчера, с 18:00 сегодня). Онбординг - цепочка `router.replace` после старта, последний шаг (причины) сейчас ведет на `/`. В SDK 57 локальные уведомления и категории с кнопками работают в Expo Go, пуши - нет.

## Goals / Non-Goals

**Goals:**

- одна точка, которая по текущим данным заново строит все расписание;
- расписание - чистая функция с тестами, включая переход на летнее время;
- форма уведомлений общая для онбординга и настроек, как форма трат.

**Non-Goals:**

- фоновая обработка кнопок без открытия приложения (`registerTaskAsync`);
- точечное планирование и отмена по id отдельных уведомлений.

## Decisions

### Слайс `features/notifications`

Расписание читает настройки, итоги дня и вечеринки, то есть несколько сущностей, поэтому это фича. В ней:

- `model/types.ts` - `NotificationPrefs`: `{ dayReview: { on, time }, risk: { on, days: Partial<Record<0..6, number>> }, party: { on } }`, время в минутах от полуночи, день недели как у `Date.getDay()` (0 - воскресенье);
- `api/prefs.ts` - `getPrefs(db)`/`savePrefs(db, prefs)`, ключ `notifications` в `settings`. Нет строки - все выключено, время и дни по умолчанию (21:00; пт и сб 17:00);
- `model/plan.ts` - чистая `plan(prefs, now, { reviewDates, partyDays, activeParty })` → список `{ kind, at, data }`;
- `model/sync.ts` - `syncNotifications(db)`: прочитать данные, `cancelAllScheduledNotificationsAsync`, запланировать `plan(...)` DATE-триггерами;
- `model/setup.ts` - канал Android `reminders` и три категории с кнопками, вызывается один раз при старте;
- `model/useNotificationResponse.ts` - обработка тапов и кнопок;
- `ui/NotificationForm.tsx` (контролируемая: `value`, `onChange`) и `ui/AutostartHint.tsx`, их подключают страницы `onboarding` и `settings`.

Страницы раскладку не знают: они зовут `syncNotifications(db)` после своих действий и рисуют форму.

### Перепланировать все целиком

Каждая синхронизация снимает все запланированные уведомления и ставит заново. Альтернатива - хранить id и снимать точечно ("итоги за сегодня заполнены → снять сегодняшнее"). Это больше состояния и больше мест, где его можно потерять, а уведомлений у нас не больше 29. Параллельные вызовы выстраиваем в цепочку промисов на уровне модуля, иначе две синхронизации могут перемешать cancel и schedule и оставить дубли.

Когда синхронизируем:

- при старте приложения и при каждом возврате в него (`AppState` → `active`);
- после записей, которые меняют план: сохранение итогов дня, ответ "без алкоголя" или "не пошел" на "Сегодня", срыв из вечеринки, удаление срыва на "Прогрессе" (вечеринка снова идущая), старт вечеринки и смена конца в режиме компании, изменение настроек, шаг онбординга, ответ "Без алкоголя" из уведомления.

Синхронизацию на фокусе "Сегодня" отбросили: она лишний раз перепланировала все при каждом переключении табов и пропускала случай, когда итоги открыли из уведомления поверх другого таба.

### Разовые уведомления на 14 дней вперед

`plan` проходит по 14 календарным дням от `now` и для каждого строит момент через `new Date(y, m, d + i, h, min)`, чтобы локальное время не съезжало на переходе на летнее время. Повторяющийся DAILY/WEEKLY-триггер не подходит: он не умеет пропустить один день, а спека требует не напоминать про уже сделанное.

- итоги дня: если включены, момент в будущем и `reviewDay(at)` нет среди дат сохраненных итогов. Сравниваем по `reviewDay`, а не по календарной дате, чтобы "Заполнить" открывало ровно тот день, о котором напомнили, даже если время раньше 18:00;
- дни риска: если включены, день недели есть в `days`, момент в будущем и `toDay(at)` нет среди дней начала неудаленных вечеринок;
- "как прошло?": если включено, есть идущая вечеринка и `expectedEndAt > now`.

Не больше 14 + 14 + 1 уведомлений, лимит Android около 500. 14 дней - запас на случай, если приложение долго не открывают.

### Кнопки и тапы

Категории `dayReview` (`fill`), `risk` (`company`), `party` (`sober`, `drank`). Все кнопки с `opensAppToForeground: true`. Кнопки "Сегодня пропущу" и "Сегодня дома" из `docs/idea.md` убрали: кнопка без открытия приложения при убитом приложении обрабатывается только фоновой задачей TaskManager (нативный `expo-task-manager`), а без нее уведомление остается в шторке. Они ничего не записывают, смахнуть уведомление можно и так. В `data` кладем `kind` и для вечеринки `partyId`.

`useNotificationResponse` в корневом layout (внутри `SQLiteProvider`) берет `useLastNotificationResponse()`, это покрывает и холодный старт, и живое приложение. Обработанный ответ сбрасываем через `clearLastNotificationResponseAsync`, чтобы он не сработал повторно. Маршруты:

| ответ             | действие                                                              |
| ----------------- | --------------------------------------------------------------------- |
| тап или `fill`    | `/day-review?day=<день из data>`                                      |
| тап или `company` | `/company`                                                            |
| тап `party`       | `/`                                                                   |
| `sober`           | если `partyId` - идущая вечеринка, `setPartyResult(sober)`; затем `/` |
| `drank`           | если идущая - `/relapse?partyId=...`, иначе `/`                       |

Проверка "вечеринка еще идущая" нужна для старого уведомления, на которое уже ответили на карточке. Если онбординг не пройден, layout табов и так уведет на `/onboarding`.

`setNotificationHandler` показывает уведомление и когда приложение открыто.

### Разрешение

Канал создаем до запроса: на Android 13 без канала системный диалог не появится. Запрашиваем `requestPermissionsAsync` только когда сохраняются настройки, где включен хоть один вид, и статус еще `undetermined`. Состояние для настроек берем `getPermissionsAsync` при фокусе экрана. Если отказано, строка "уведомления выключены в системе" и `Linking.openSettings()`. Переключатели при этом работают: расписание ставится, система его просто не показывает, и после разрешения все заработает без повторной настройки.

### Xiaomi и подобные

`Platform.OS === 'android'` и `Platform.constants.Manufacturer` из списка xiaomi, redmi, poco, huawei, honor, oppo, vivo, realme, oneplus (без учета регистра). Без новой зависимости: `expo-device` дал бы то же самое. На Xiaomi кнопка открывает экран автозапуска MIUI/HyperOS по имени компонента (`com.miui.securitycenter/com.miui.permcenter.autostart.AutoStartManagementActivity`) через `expo-intent-launcher`: `Linking` умеет только action, а в настройках приложения на HyperOS пункта автозапуска нет, пользователь его не находит. Если экрана нет или это другая прошивка - `Linking.openSettings()`. Компоненты других прошивок добавим, когда будет на чем проверить.

### Онбординг

Шаг причин ведет на `/onboarding/notifications` вместо `/`. Шаг держит форму в состоянии страницы со всеми тремя видами включенными. "Дальше" сохраняет, при необходимости запрашивает разрешение, синхронизирует и делает `replace` на `/onboarding/autostart` (если устройство из списка) или `/`. "Пропустить" ничего не сохраняет. Шаг про автозапуск: `AutostartHint` и "Готово" → `replace('/')`. Если онбординг прервали на этих шагах, он считается пройденным (строка в `habit` уже есть), уведомления остаются выключенными, это совпадает с "только по согласию".

### Настройки

Новая секция `NotificationsSection` в `pages/settings/ui` рисует `NotificationForm` и `AutostartHint`, данные и сохранение - в `model/useNotificationSettings.ts`: каждое изменение сразу `savePrefs`, запрос разрешения и `syncNotifications`. Время выбираем новым `TimeField` в `shared/ui` (только время, `DateTimePickerAndroid.open({ mode: 'time' })`, значение в минутах). Дни риска - чипы `weekdays` (они с понедельника, индекс переводим в `getDay`), у выбранного дня строка со своим временем; новый день получает 17:00.

### Тексты

Тексты уведомлений и формы - в `features/notifications/i18n.ts`. Текст уведомления берется из языка на момент синхронизации; язык определяется при старте, так что после смены языка системы тексты обновятся при следующем открытии приложения.

## Risks / Trade-offs

- [MIUI/HyperOS убивает приложение и не показывает уведомления] → подсказка про автозапуск в онбординге и настройках. Запланированные DATE-триггеры живут в AlarmManager и обычно приходят, но гарантий нет.
- [Кнопки категорий могут вести себя не так, как ожидаем] → первая задача - проверка на телефоне в development build. Если кнопки не работают, тап по уведомлению открывает тот же экран.
- [Ответ "Без алкоголя" открывает приложение] → осознанно: без фоновой задачи иначе не записать, а показ "Сегодня" подтверждает, что ответ принят.
- [Уведомления кончатся, если приложение не открывать больше 14 дней] → принимаем: человек, который две недели не открывает приложение, вряд ли ждет напоминаний.
- [Перезагрузка телефона] → `expo-notifications` восстанавливает запланированные уведомления после перезагрузки сам.

- [В Expo Go на Android `expo-notifications` не работает, вопреки докам: корневой импорт падает на регистрации пуш-токена, а после обхода нет нативного менеджера каналов] → переходим на development build (`expo-dev-client`, профиль `development` в `eas.json`), Expo Go для проекта больше не используем.

- [Без разрешения на точные будильники `expo-notifications` ставит неточный (`setAndAllowWhileIdle`), HyperOS в фоне откладывает его надолго, а синхронизация, прошедшая после назначенного времени, снимает его совсем] → в `app.json` `USE_EXACT_ALARM` (выдается сразу, Android 13+) и `SCHEDULE_EXACT_ALARM` (Android 12). Google Play разрешает `USE_EXACT_ALARM` только будильникам и календарям: перед публикацией в Play заменить на `SCHEDULE_EXACT_ALARM` с подсказкой включить "Будильники и напоминания" в системных настройках.

## Migration Plan

Схема не меняется, `user_version` тот же. Новые зависимости `expo-notifications` и `expo-dev-client` ставятся через `npx expo install`, плагин уведомлений добавляется в `app.json`, на телефон ставится development build из EAS. Откат - убрать зависимость и вызовы синхронизации; ключ `notifications` в `settings` ничему не мешает.
