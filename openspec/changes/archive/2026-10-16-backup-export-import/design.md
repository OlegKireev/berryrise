# Design

## Context

Схема целиком лежит в `src/shared/db/migrations.ts`: массив миграций, версия хранится в `PRAGMA user_version`, `migrate` применяет каждую миграцию в своей транзакции. Сейчас версия одна. Восемь таблиц: семь со служебными колонками `id/createdAt/updatedAt/deletedAt` и `settings` (key/value). Для разработки есть `resetDatabase`: он удаляет таблицы и обнуляет версию.

`expo-file-system` уже стоит в `node_modules` транзитивной зависимостью `expo` (`~57.0.7`) и автолинкуется в текущий dev build. В нем есть `File.pickFileAsync({ mimeTypes })`, `Paths.cache` и чтение и запись файла. `expo-sharing` подключен плагином. Экраны "Сегодня", "Прогресс", карточка дня, причины и настройки перечитывают данные на фокусе (`useFocusEffect`). Табы проверяют наличие `habit` при монтировании и без него уводят на онбординг.

## Goals / Non-Goals

**Goals:**

- Сделать восстановление атомарным: одна транзакция от удаления старых таблиц до последней миграции.
- Принимать файлы старых версий схемы без отдельного кода конвертации под каждую версию.
- Держать разбор и проверку файла чистой функцией с тестом.

**Non-Goals:**

- Проверка содержимого записей по полям в JS. Это делают `NOT NULL` и `CHECK` схемы, их ошибка откатывает транзакцию.
- Потоковая обработка больших файлов. Данных за годы - сотни килобайт, файл целиком помещается в памяти.

## Decisions

### Фича `features/backup`

Экспорт и импорт работают со всеми таблицами сразу, поэтому они не принадлежат одной сущности. По FSD это фича, SQL в фичах разрешен. Состав:

- `model/format.ts` - чистая логика: `backupFileName(date)`, `parseBackup(text, currentVersion)` возвращает либо `{ version, tables }`, либо код ошибки `notBackup` / `tooNew`. Рядом тест.
- `api/` - `dumpTables(db)` (`SELECT *` по всем таблицам из `sqlite_master`) и импорт через `restoreDatabase` из `shared/db`.
- `model/useExport.ts`, `model/useImport.ts` - хуки с файлами, `Alert` подтверждения и ошибок, перепланированием уведомлений и навигацией.
- `i18n.ts` - тексты кнопок, пояснения и ошибок.

`features/backup` импортирует `syncNotifications`, `getPrefs`, `anyOn` и `ensurePermission` из `features/notifications`, а FSD запрещает слайсам одного слоя импортировать друг друга. Поэтому перепланирование после импорта зовет страница: хук импорта принимает колбэк `onImported`. Страница настроек и `IntroPage` передают туда функцию, которая вызывает `syncNotifications` и `ensurePermission`, а потом переходит дальше. Альтернатива - положить импорт прямо в `pages/settings`. Отклонена: импорт нужен и онбордингу, а это тоже слайс одного слоя.

### Восстановление в `shared/db`: миграции до версии файла внутри одной транзакции

В `migrations.ts` появляется `restoreDatabase(db, version, fill)`. Внутри одного `withExclusiveTransactionAsync` она:

1. удаляет все таблицы, как `resetDatabase`;
2. применяет миграции `[0, version)`, то есть строит схему ровно той версии, из которой пришел файл;
3. вызывает `fill(tx)`, который вставляет строки файла;
4. применяет оставшиеся миграции до текущей версии и ставит `user_version`.

Ошибка на любом шаге откатывает все, включая `DROP TABLE`: в SQLite DDL транзакционный. Так файл старой версии проходит те же миграции, что и живая база при обновлении, и отдельных конвертеров нет. Еще проще было бы принимать только файл текущей версии. Отклонено: после первой новой миграции все старые копии перестали бы открываться.

`resetDatabase` и `migrate` не меняются. Общий список миграций используется изнутри модуля.

### Вставка только известных колонок

`fill` идет по таблицам из `sqlite_master` (схема версии файла уже создана), для каждой берет колонки из `PRAGMA table_info` и вставляет строки `tables[имя] ?? []` только по этим колонкам, параметрами `?`. Имена таблиц и колонок берутся из базы, а не из файла, поэтому ключи файла не попадают в SQL как идентификаторы. Лишнее поле в записи игнорируется, недостающее становится `NULL` и, если оно обязательно, роняет транзакцию. Это и есть ответ "файл поврежден".

### Формат файла

```json
{
  "app": "dev.olegkireev.quit",
  "schemaVersion": 1,
  "exportedAt": 1792170309000,
  "tables": { "habit": [{...}], "relapse": [], "dayReview": [], "party": [], "reason": [], "reply": [], "contact": [], "settings": [] }
}
```

Строки идут как есть из базы: JSON-колонки остаются строками, время в epoch ms. Это не самый читаемый вид, зато импорт - обратная вставка без преобразований. `parseBackup` проверяет: JSON - объект, `app` совпадает, `schemaVersion` целое и `>= 1`, а если оно больше текущего, возвращает `tooNew`; `tables` - объект, каждое значение в нем - массив объектов. Таблицы, которой нет в файле, восстанавливаются пустыми, лишние ключи игнорируются. Отдельного списка таблиц в коде нет, его не нужно держать в синхроне со схемой.

### Экспорт

Кнопка "Экспортировать" одна, по нажатию `Alert` с тремя кнопками: "Сохранить на телефон", "Отправить", "Отмена". Больше трех кнопок `Alert` на Android не показывает, а здесь их ровно три. Дамп и JSON собираются после выбора.

- **Отправить**: `new File(Paths.cache, имя)`, `JSON.stringify` дампа, затем `Sharing.shareAsync(uri, { mimeType: 'application/json' })`. Файл в кэше не удаляем, это делает система. Если меню "Поделиться" закрыли, это не ошибка.
- **Сохранить на телефон**: файл пишется в `Paths.cache`, затем `saveDocuments({ sourceUris, mimeType, fileName })` из `@react-native-documents/picker` открывает системный диалог "Сохранить как" (`CREATE_DOCUMENT`) и копирует файл туда. Отмену (`errorCodes.OPERATION_CANCELED`) гасим молча, ошибку или `error` в ответе показываем. После записи показываем тост "Сохранено: <имя>": в отличие от "Поделиться", здесь результат известен точно. На iOS тот же вызов открывает "Сохранить в Файлы".

Почему не другие способы (проверено на эмуляторе):

- `Directory.pickDirectoryAsync` из `expo-file-system` (выбор папки, `OPEN_DOCUMENT_TREE`): Android 11+ не дает выбрать Download и корень памяти ("Can't use this folder").
- `CREATE_DOCUMENT` через `expo-intent-launcher`: модуль отдает в `data` строку `Intent.toString()` с сокращенным адресом, записать по ней нельзя. Править его через `yarn patch` не стали.
- Свой Expo-модуль на Kotlin: рабочий вариант, но выбрали готовую библиотеку.

Добавить свой пункт прямо в системное меню "Поделиться" (chooser с intent `CREATE_DOCUMENT`) нельзя без своего нативного кода, а это пересборка. Поэтому выбор сделан своим `Alert`.

### Импорт: экраны и навигация

- **Настройки** (`settings/backup`): `File.pickFileAsync({ mimeTypes: ['application/json', 'application/octet-stream', 'text/plain'] })`: облака и мессенджеры часто отдают JSON как `octet-stream` или `text/plain`. Решает содержимое (`parseBackup`), а не тип. Дальше `Alert` с подтверждением, `restoreDatabase`, `onImported`, затем `router.dismissAll()` и переход на "Сегодня". Экраны перечитают данные на фокусе.
- **Онбординг** (`IntroPage`): то же без подтверждения. После импорта, если в `habit` есть неудаленная строка, выполняется `router.replace('/')`: табы монтируются заново и находят `habit`. Если строки нет, `Alert` "в копии нет старта", и пользователь остается на шаге.

Медали заново не празднуются сами собой: `seenAchievements` лежит в `settings` и приходит из файла, а `celebrate.ts` при наличии строки показывает только новые.

### Уведомление об успехе

Успешный импорт и сохранение на телефон подтверждаются тостом: `toast(text)` в `shared/ui`, на Android `ToastAndroid` (встроен в React Native, без зависимостей), на iOS системных тостов нет, там `Alert`. Snackbar из Material не берем: нужна библиотека, а действия "Отменить" здесь нет. Ошибки остаются алертами: их надо прочитать.

### Строка хаба

Иконка `archive` из lucide добавляется строкой в мапу `Icon.tsx`. Подпись "Экспорт и импорт" используется и в хабе, и в заголовке экрана в корневом `Stack`. Поэтому она идет в `shared/i18n/common.ts`, как подписи других разделов.

### Зависимость

`npx expo install expo-file-system` записывает в `package.json` ту же версию, что уже стоит. Нативный код от этого не меняется, config plugin не нужен.

`@react-native-documents/picker` - новая нативная зависимость (автолинкуется, config plugin не нужен, `app.json` не меняется). **Нужна пересборка dev build**, локально квоту EAS она не тратит.

## Risks / Trade-offs

- [Файл содержит заметки и срывы в открытом виде] → Пояснение на экране экспорта. Шифрование вне рамок.
- [Неудачная транзакция на огромном файле держит базу] → Объемы маленькие. Если станет больно, импорт можно будет разбить на пакеты вставок.
- [Импорт стирает данные, которые новее файла] → Подтверждение с явным текстом. Перед импортом можно сделать экспорт, и подсказка на экране об этом напоминает.
- [`pickFileAsync` на части устройств не показывает `.json`] → Широкий фильтр MIME-типов и проверка содержимого. Если на телефоне не хватит и его, фильтр снимаем совсем.
- [Будущая миграция, которая трансформирует данные, должна работать и на только что вставленных строках файла] → Так она и так работает на живой базе. Отдельного требования нет.

## Migration Plan

Схема базы не меняется, миграции нет. Откат - удалить фичу и строку хаба, данные пользователя не затрагиваются.
