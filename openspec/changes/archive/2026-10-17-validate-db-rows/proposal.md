# Proposal

## Why

Типы строк в `entities/*/model/types.ts` - обещание, которое никто не проверяет: `getAllAsync<Relapse>` это тот же `as`, только спрятанный в дженерик. Если форма данных меняется (убрали вариант настроения, причину, место), а миграцию для старых строк забыли, старые значения проходят как "валидные" и ломают экран где-то далеко (`t(\`mood.${m}\`)`покажет ключ, статистика посчитает мусор). Отдельная дыра - импорт: SQLite из-за type affinity примет в`at INTEGER`строку, в`mood INTEGER` число 99, а проверяет файл только обертку.

Нужна схема строки, которая одновременно задает тип и проверяет данные на чтении, чтобы тип и проверка не могли разойтись.

## What Changes

- Новая зависимость `zod` (чистый JS, пересборка не нужна). Перед переходом - спайк на Hermes в dev build.
- В каждой сущности (`habit`, `relapse`, `dayReview`, `party`, `reason`, `reply`) появляется схема строки, тип строки становится `z.infer` от нее. Ручные типы строк в `types.ts` уходят.
- JSON-колонки (`places`, `hardships`, `helpers`, `drinkKeys`, `drinkCustoms`, `habit.drinks`) разбираются в `api/` сущности: наружу строка выходит уже с массивами и объектами, а функции записи принимают разобранные значения и сами делают `JSON.stringify`. `parseList`/`parseCounts` из страниц (`useDayCard`, `useDayReview`, `useCompany`, `useInsights`, `useToday`, `useSpendingForm`) уходят.
- Поведение при несовпадении со схемой:
  - неизвестный элемент списка выкидывается, неизвестное значение в поле, где `null` осмыслен, становится `null`;
  - строка, у которой сломан "скелет" (служебные поля, время, дата, обязательный вариант), в `relapse` и `habit` роняет чтение ошибкой: без нее стрик тихо соврал бы в хорошую сторону; в остальных таблицах такая строка пропускается;
  - каждый такой случай пишется в журнал (таблица, колонка, id строки, без самого значения), не чаще раза за запуск на колонку.
- Импорт проверяет все таблицы теми же схемами после миграций, внутри той же транзакции: строка со сломанным скелетом отменяет импорт с сообщением "файл поврежден".

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `local-data`: новое требование - данные из базы проверяются при чтении, устаревшие варианты не ломают экраны, сломанная запись срыва или привычки не дает тихо пересчитать стрик.
- `backup`: "Импорт атомарный" и "Проверка файла" - файл с недопустимыми значениями в записях отклоняется целиком, а не только при нарушении NOT NULL и CHECK.
- `error-log`: "Что попадает в журнал" - добавляются данные из базы, не прошедшие проверку.

## Impact

- Код: все `entities/*/api` и `model/types.ts`, страницы и фичи, которые сейчас парсят JSON-колонки сами, `features/backup` (проверка после импорта), `shared/db` (`restoreDatabase` получает проверку после миграций, хелперы схем для JSON-колонок), `shared/lib/logEntries.ts` (тег `db`).
- Зависимости: `zod` (JS-only, без нативного кода, dev build пересобирать не нужно).
- Схема базы и миграции не меняются.
- Документация: `CLAUDE.md` (стек, раздел про сущности и запрет `as`).

## Вне рамок

- JSON в таблице `settings` (уведомления, показанные медали, свои причины и напитки): там уже есть ручные парсеры с фолбэками, перевод на схемы - отдельным шагом, если понадобится.
- `STRICT`-таблицы и новые CHECK в SQLite: потребовали бы миграцию с пересозданием таблиц.
- Починка уже битых данных: схема только сигналит и подстраховывает, чинит по-прежнему миграция.
- Служебные запросы `PRAGMA`, `sqlite_master` и дамп экспорта: это не строки сущностей.
